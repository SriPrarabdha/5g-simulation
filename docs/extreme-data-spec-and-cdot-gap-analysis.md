# Extreme simulation data specification and C-DOT comparison guide

Status: executable as-built specification for the seed-`20260805` extreme profile  
Audience: C-DOT telemetry, packet-core, testbed, forecasting, and optimization meeting  
Evidence rule: all simulation values are synthetic unless explicitly identified as a measured workstation benchmark or a public C-DOT figure

## 1. Executive answer

The extreme run is suitable for:

- exercising the complete offline data path for 16 weeks;
- producing a large, labeled, deterministic training corpus;
- training one arrival/UL/DL model for each of 96 controllable groups;
- testing capacity loss, near-outage, congestion, and surge regimes; and
- validating UPF eligibility, directional capacity, session capacity, locality,
  policy fallback, artifact schemas, and reproducibility.

It is not yet evidence that the model matches C-DOT traffic. In particular:

- the 16-million-UE value is a scenario label, not a population-conserving UE model;
- the calibrated day carries about 121.08 PB/day, 40.4 times the 3 PB/day
  reference point; because C-DOT reports **more than** 3 PB/day, the true
  multiple relative to that deployment is lower than 40.4;
- the batch artifacts are not Prometheus N3/N6 packet and byte counters;
- joint per-UPF/group boundary demand is now available, but per-UPF carried,
  queued, and dropped traffic is not attributed back to individual groups;
- mobility, packet sizes, packet rate, CPU, memory, counter resets, telemetry
  gaps, and restart records are not generated by this profile; and
- the current online controller acts on the immediate next 10-minute bucket,
  not the one-bucket-ahead `11:50 -> 12:00–12:10` timing in the mail.

Therefore the answer to “does it satisfy the mail?” is:

> It satisfies most of the synthetic-history, topology, capacity, eligibility,
> forecast-schema, and optimizer requirements. It only partially satisfies the
> Prometheus telemetry and timing requirements, and it does not establish
> C-DOT realism without C-DOT-provided counters, labels, topology, testbed
> scale, and capacity measurements.

Use this run as an **extreme stress/pretraining corpus**, not as the final
C-DOT-calibrated baseline.

## 2. The actual data flow

The implemented extreme-history path is:

```text
extreme profile JSON
        |
        v
seeded 16-week manifest (groups, UPFs, hourly factors, faults)
        |
        v
30-second static-controller macro simulation
        |
        +--> run.jsonl
        +--> run.parquet: per-tick arrivals and UPF state + 10-minute joint
        |                 (UPF, zone, DNN, S-NSSAI, 5QI) demand snapshots
        +--> selection-audits.parquet: deterministic 1-in-5,000 sample
        +--> metadata.json: hashes + aggregate summary
        |
        v
20 consecutive 30-second rows -> one 10-minute training bucket
        |
        v
calendar-ridge direct forecasts for 10, 20, ... 80 minutes
        |
        v
separate predictive run -> HiGHS allocation -> validated policy weights
```

The implemented but not yet wired live path is:

```text
Prometheus instant queries -> TelemetrySample -> counter reconstruction
    -> 10-minute MetricBucket

Missing production wiring:
MetricBucket -> the same DemandObservation input used by the forecaster
```

The long extreme history run uses the static capacity-weighted controller. It
does not run the forecaster and HiGHS optimizer at every boundary. This is
intentional for exogenous history generation. Train the bundle first, then run
a separate predictive evaluation with exactly matched seeds.

## 5. Exact probabilistic model

### 5.1 Determinism and random streams

- A manifest seed fixes all scenario events.
- Each group has independent SHA-256-derived random streams for arrivals and
  holding times.
- Repeating the same manifest, controller, and seed produces the same logical
  simulation result.
- Changing the run seed changes arrivals and lifetimes while keeping the frozen
  manifest topology and event schedule.

### 5.2 Arrivals

For group `g` at 30-second tick `t`:

```text
N(g,t) ~ Poisson(base_arrivals(g) * arrival_factor(g,t))
```

The Poisson sampler is exact for the configured mean by summing independent
Poisson chunks. It does not use a Gaussian approximation.

The absolute hourly arrival factor combines:

- a service-specific deterministic daily curve;
- a service-specific weekend multiplier;
- independent group/week noise sampled uniformly from `[0.86, 1.16]`; and
- any active flash-crowd multiplier.

Factors are updated once per simulated hour and held constant for the 120
30-second ticks in that hour.

### 5.3 Holding times and offered load

- Holding time is a discrete uniform integer draw over the class range shown
  in section 4.
- Every active session in one class has the same fixed UL and DL Mbps.
- There is no lognormal/Pareto holding-time draw, packet-size distribution,
  rate distribution, or per-session bitrate variation in this executable
  profile.
- Offered load is the sum of fixed per-session rates for all active sessions.
- Sessions are represented in aggregate cohorts after placement, but every new
  session is individually passed through deterministic UPF selection.

### 5.4 Placement

The static training controller assigns weights from each eligible UPF’s safe UL
plus safe DL capacity. Each new session is placed with deterministic weighted
rendezvous hashing. The health gate removes unavailable UPFs and renormalizes
weights. Session-capacity admission is checked after selection.

### 5.5 What is not in the executable model

The following mechanisms appear in the broader target traffic-model design but
are not produced by the current extreme generator:

- AR(1) latent traffic state;
- two-state Markov burst residuals;
- lognormal or bounded-Pareto rate and holding-time distributions;
- persistent UE identity or population conservation;
- UE mobility or origin/destination transitions;
- packet sizes, packets/s, flows, TEIDs, radio scheduling, retransmissions, or
  protocol overhead;
- correlated multi-class stadium lifecycle effects;
- telemetry gaps, counter resets, exporter restarts, or stale samples; and
- compute utilization derived from packet processing.

These are calibration and implementation gaps, not hidden features of the run.

## 6. Scenario and stress-event catalogue

The full manifest contains 258,048 hourly group-factor records plus 608 fault
records.

| Scenario family | Episodes or records | Sampling/model | Observable effect in static history |
|---|---:|---|---|
| Daily/weekly demand regimes | 258,048 factor records | Service curve × weekend factor × `U(0.86,1.16)` weekly factor | Group arrivals and derived group demand change |
| Flash crowds | 192 episodes | 12/week; one random group; 2–10 h; multiplier `U(2.5,8.0)` | Large localized arrival/demand spikes |
| Capacity brownouts | 128 episodes | 8/week; 1–8 h; UL factor `U(0.18,0.70)`; DL factor capped at UL+0.12 | Capacity, queueing, drops, and later static weights change |
| Near-total UPF outage | 48 episodes | 3/week; 1–4 h; health=`degraded`, capacity=1% | Severe queue/drop stress; this is not a hard `unavailable` state |
| Path-latency incident | 80 episodes | 5/week; 1–6 h; add `U(25,140)` ms | Applied internally, but static history does not store latency and static placement ignores it |

Surge episodes are folded into the hourly arrival-factor records; there is no
separate `surge_id` column in the output. Fault records are present in the
manifest, but `run.parquet` stores their resulting UPF health/capacity rather
than a separate event table.

## 7. UPF topology, capacity, and eligibility

### 7.1 Topology

- 16 edge UPFs: two per traffic zone;
- 4 regional UPFs: one for each two-zone region;
- 4 central UPFs;
- each traffic group can use exactly 6 UPFs: 2 local edge, 2 regional, and 2
  central; and
- every UPF declares path latency to every traffic zone.

This is a logical eligibility topology. It is not a packet-network graph: there
are no links, link capacities, N3/N6/N9 paths, gNBs, TACs, routing tables, or
transport failures.

### 7.2 Per-instance capacity

| Tier | Count | Rated UL per UPF | Rated DL per UPF | Session cap per UPF | Safe traffic threshold | Safe session threshold | Queue limit |
|---|---:|---:|---:|---:|---:|---:|---:|
| Edge A | 8 | 480 Gbps | 1.44 Tbps | 1.44 million | 78% | 82% | 2 s |
| Edge B | 8 | 560 Gbps | 1.28 Tbps | 1.44 million | 78% | 82% | 2 s |
| Regional | 4 | 1.12 Tbps | 2.40 Tbps | 3.52 million | 80% | 85% | 3 s |
| Central | 4 | 1.92 Tbps | 3.84 Tbps | 5.12 million | 75% | 85% | 4 s |
| **Total** | **24** | **20.48 Tbps** | **46.72 Tbps** | **57.60 million** | Mixed | Mixed | Mixed |

These values are unsupported synthetic assumptions. They must be replaced with
C-DOT’s tested capacity envelope by UPF hardware/software profile.

### 7.3 Latency model

- Local edge latency is 1.5 ms.
- Remote edge latency is `10 + 3 × zone-index distance` ms.
- Regional latency is `5 + 2 × zone-index distance` ms.
- Central latency is `12 + 1.5 × target-zone index` ms.

The predictive optimizer can use latency as a locality cost and optionally as
a hard maximum. The default maximum is unset. The static training controller
does not use path latency.

### 7.4 Overload detection without CPU or memory telemetry

CPU and memory are optional in the mail and are not required for the first
traffic-diversion decision. The demo calculates an operating index for each
UPF as the maximum of:

```text
carried UL Mbps / safe UL Mbps
carried DL Mbps / safe DL Mbps
active sessions / safe session capacity
```

The UI reports low headroom from 0.82 and overload at 1.0. Queue growth,
dropped bytes, rejected bytes, establishment failures, health, and forecast
slack provide corroborating service-level signals. The reactive controller
removes high-utilization UPFs from its preferred set, while the predictive
optimizer allocates forecast demand against residual UL, DL, and session
headroom. Both affect new sessions; existing sessions are not migrated.

The demo API currently returns CPU and memory values calculated from traffic
and session utilization. Those are explicitly synthetic display proxies, not
independent measurements, and neither overload detection nor optimization
uses them. Real CPU, memory, packets/s, and queue metrics remain valuable for
discovering that a UPF's effective capacity is lower than its configured rated
envelope and for calibrating heterogeneous hardware.

`offered_ul_mbps`/`offered_dl_mbps`. A group can be joined directly to the
manifest and indexed jointly with its serving UPF.

Important limitation: joint values are boundary offered-demand snapshots.
Carried bytes, queue, and drops remain aggregate by UPF and direction because
the shared UPF service queue has no measured per-group attribution rule. The
campaign also does not claim N3/N6 interface-level counters.

### 8.3 `selection-audits.parquet`

Schema version: `selection-audit/1.0`  
Granularity: deterministic systematic sample, one row for session sequence
`0, 5000, 10000, ...` within each group

Fields are timestamp, hashed session identity, winning rendezvous hash, zone,
DNN, S-NSSAI, eligible UPFs, requested weights, selected UPF, policy ID, and
selection reason. Raw UE/session identity is never persisted. 5QI is omitted
because it is not part of the v1 selection key.

### 8.4 `run.jsonl`

This is the readable audit adapter. It contains:

1. one `simulation_metadata` record;
2. all `simulation_step` records; and
3. all retained `selection_audit` records.

It duplicates the canonical Parquet content and is not the forecaster’s input.

### 8.5 `metadata.json`

Contains campaign/scenario/controller/seed identity, absolute manifest path,
manifest and artifact SHA-256 values, Git commit, Python/component versions,
host/job metadata, creation time, filenames, and the aggregate simulation
summary.

### 8.6 Trained forecast bundle

Schema version: `trained-forecast-bundle/1.0`

The bundle contains:

- 96 group models;
- targets `new_session_count`, `new_ul_mbps`, and `new_dl_mbps`;
- direct horizons 1–8, corresponding to 10–80 minutes;
- p50 point estimates plus split-conformal p90/p95 widths;
- coefficients, median calibration bias, held-out metrics, model/source
  metadata, and checksum; and
- adaptive conformal miscoverage state for online use.

Features are intercept, last value, six-bucket rolling mean, recent trend,
one-day seasonal lag, sine/cosine time of day, and sine/cosine day of week.

The model fitter currently uses an ordered 70% train / 15% calibration / 15%
test split within each sequence. The manifest separately declares weeks 1–11,
12–13, and 14–16. Those boundaries are close but not identical; the trainer
does not yet enforce the manifest’s exact week boundaries.

## 9. What the trainer actually consumes

For every 20-row chunk of `run.parquet`, the trainer:

1. sums `group_arrivals` for each group;
2. computes group new-session demand as that count;
3. computes group new UL/DL demand as count × the class’s fixed Mbps/session;
4. averages active sessions and offered Mbps per UPF across all 20 rows as the
   residual-load feature; and
5. creates one `DemandObservation` per group.

It does not currently use:

- p95 or maximum UPF throughput across the full 10-minute bucket;
- per-group measured throughput counters;
- packet counters;
- queue, drop, or rejection fields as forecast targets;
- selection audits;
- event IDs or event type as features; or
- CPU/memory/packet-processing metrics.

The generic telemetry pipeline can reconstruct counter deltas and calculate
duration-weighted total, mean, p95, max, missing fraction, resets, restarts, and
late-sample flags. That output is not wired into this trainer yet.

## 10. Forecaster and optimizer timing

### 10.1 Mail requirement

The mail’s example closes history at 11:50 and predicts 12:00–12:10. That is a
two-step target relative to the most recently closed 11:40–11:50 bucket and
allows a 10-minute actuation lead time.

### 10.2 Current implementation

- Offline bundle: supports 10–80 minute horizons.
- Current predictive controller: at boundary 11:50, closes 11:40–11:50 and
  targets 11:50–12:00 with `horizon_steps=1`.
- The selected policy affects sessions arriving immediately after 11:50.
- There is no configured 10-minute actuation delay or future activation time.

The model capability exists, but the online controller timing does not yet
match the mail’s exact example.

### 10.3 Optimizer inputs and constraints

The HiGHS linear program uses p95 by default and includes:

- new sessions, new UL, and new DL forecast per group;
- residual sessions and residual UL/DL per UPF;
- current directional capacity and safety thresholds;
- session capacity and safety threshold;
- UPF health;
- group-to-UPF eligibility;
- zone path latency;
- optional maximum latency;
- overload slack;
- locality cost; and
- change from the previous policy.

It outputs normalized group-to-UPF weights, projected per-UPF load, constraint
slack, maximum safe utilization, solver status/runtime, and fallback metadata.
It does not yet actuate a C-DOT SMF/EMS; the production actuator is a deliberate
placeholder.

## 12. Comparison with publicly documented C-DOT scale

C-DOT’s 2024–25 annual report states that its 4G/5G NSA core was integrated
with more than 75,000 RAN sites, served around 12 million subscribers, and
handled more than 3 PB/day. C-DOT’s public Bharat 5G SA page describes a
Release-16 core with control/user-plane separation, network slicing, MEC, and a

Conclusion: subscriber/session magnitude is in the same broad order as one
public national deployment number, but traffic volume is much higher and
topology detail is much lower. It is not defensible to call the profile
“C-DOT-scale” without qualification.

### 12.1 Data-volume comparison method

A C-DOT dataset-size comparison cannot be completed from public information
because UPF count and supported label combinations are not published. For 16
weeks, the basic cardinalities are:

| Resolution | Values per distinct Prometheus series |
|---|---:|
| 15-second scrape | 645,120 |
| 30-second scrape | 322,560 |
| 10-minute aggregate | 16,128 |

Multiply those values by the number of distinct series C-DOT exposes. For
example, a fully crossed synthetic layout with 24 UPFs × 2 interfaces (N3/N6)
× 2 directions × 96 traffic groups would create 9,216 throughput series, or
about 2.97 billion raw values at a 30-second scrape interval before packet,
session, compute, or quality metrics are added. This is only a cardinality
illustration; Prometheus labels may not support that cross-product.

The present simulation is smaller and structurally different: it stores
30,965,760 group-arrival counts, 7,741,440 aggregate UPF tick records, and at
most 9,289,728 joint `(UPF, group)` 10-minute records. It does not store the
fully crossed joint series every 15 or 30 seconds. Consequently, its runtime
and file size cannot be used to predict the size of a fully labeled C-DOT
Prometheus export.

## 14. Recommendation before the 8–12-hour run

Run the current profile if the goal is to stress the pipeline, generate many
group-bucket examples, and test extreme capacity regimes.

Do not use its forecast accuracy as evidence of expected C-DOT production
accuracy. For a C-DOT-comparable training/evaluation release:

1. obtain the meeting inputs in section 13;
2. preserve this profile as `extreme`;
3. create a separate `cdot-calibrated` profile with measured daily volume,
   session rate, holding times, UPF capacity, and label availability;
4. validate which joint class/location labels C-DOT actually exports;
5. wire live `MetricBucket` output into the forecaster;
6. implement the requested one-bucket actuation lead time; and
7. evaluate synthetic-pretrained models on untouched C-DOT history.

If only 3 PB/day is used as a temporary anchor, the current 121.08 PB/day
carried load is 40.4× that reference point. Because the reported deployment
handles more than 3 PB/day, this is an upper bound on the comparison ratio.
Reducing load toward a measured C-DOT anchor while keeping an 8–12-hour
experiment should be done with more seeds and scenario families, not by
preserving an unrealistic per-session traffic rate.
