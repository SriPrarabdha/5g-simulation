STEP 3 -- "Did you EVER have this data?"
======================================================================

    upf_n3_downlink_packets_session_class_total_byte
        stored series      : 32
        newest reading was : 04:08:18 UTC (27 Aug, 09:38:18 IST)
        i.e.               : 13.6 hours ago
    pfcp_sessions_total
        stored series      : 8
        newest reading was : 04:08:18 UTC (27 Aug, 09:38:18 IST)
        i.e.               : 13.6 hours ago

  ==> Yes -- the data IS there. 32 stored series for uplink, 32 for
      downlink. That proves two things straight away:
        * the metric names we use are correct
        * your UPF exporters were publishing correctly

      But the newest reading is from 09:38:18 IST this morning.
      Nothing has arrived since. The data is frozen at that moment.

      All three metrics stop at the SAME SECOND. That matters: if one
      UPF had crashed, only that UPF's numbers would stop. Everything
      stopping together, to the second, is the signature of a
      configuration change -- not a hardware or exporter failure.


======================================================================
STEP 4 -- "Prometheus, what are you collecting FROM?"
======================================================================

  This is the important one.

  Prometheus does not sit and wait for data to be sent to it. It goes
  out every few seconds and fetches data from a list of machines it
  keeps in its configuration. This command asks to see that list.

  curl 'http://192.168.218.8:29090/api/v1/targets?state=active'

  ANSWER (simplified):
    machines on the list : 1
      -> job 'prometheus'  at  http://localhost:9090/metrics   [up]
    filtered-out entries : 0

  ==> HERE IS THE PROBLEM.

      The list contains 1 entry, and that entry is Prometheus
      itself. ("localhost:9090" is Prometheus's own internal address --
      it is collecting its own health statistics, nothing more.)

      There are NO UPF machines on this list. Prometheus is not asking
      any UPF for data, so naturally it has none to give us. That is
      the entire explanation for the empty result in Step 2.

      One more detail: filtered-out entries = 0. This rules out the
      gentler explanation. If the UPF jobs were still written in
      prometheus.yml but being excluded by a relabel rule, they would
      appear here as filtered out. They do not appear at all -- so they
      are simply no longer in the configuration file.

  curl --get http://192.168.218.8:29090/api/v1/query \
       --data-urlencode 'query=prometheus_config_last_reload_success_timestamp_seconds'

    Config file last loaded   : 04:20:36 UTC (27 Aug, 09:50:36 IST)
    Did that load succeed?    : 1    (1 = yes, no errors)

  ==> Now put the three times side by side:

        09:38 IST   last UPF reading arrives
        09:47 IST   Prometheus restarts

                    and that file lists only one job: itself
        since then  no UPF data at all

      Note the reload SUCCEEDED. There is no error message to hunt for
      in the logs. Prometheus did exactly what it was told; the file it
